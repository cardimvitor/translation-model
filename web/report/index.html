How to read the scores. Exact is the share of outputs that match a reference English name word for word (after lowercasing). chrF (0–100) is a character-overlap score that gives partial credit, e.g. "cotton t-shirt" vs "cotton tee shirt". Two test sets, never used in training: Labels = 320 product labels I wrote by hand in 16 languages; Real names = 993 real marketplace product names from the Amazon Berkeley Objects set, held out before training. Accurate is the full system (Fast rules, then the small neural model when Fast is unsure); model alone is the neural model without Fast.

The final model: v6

What changed. Reviewing everything showed one weak point: the neural part was trained from nothing on 4 CPU cores, and alone it scored about 32 on the labels while the big translators score 76–95. v6 does not start from nothing. It takes a compact pretrained translator (OPUS-MT mul-en, 77M parameters, CC BY 4.0), trims its vocabulary to our 16 languages (adding the Korean pieces it lacked), and fine-tunes it for 8.5 hours on everything we had built: the v5 MAX data plus 58k new short-label pairs made from Amazon search queries. After 30 minutes it already beat every earlier model.

The default 8-bit conversion cost about 5 chrF on short labels. Scaling each output channel separately recovers most of it at the same size and speed. A 7-bit range (which would make the browser and server round identically) lost too much, so the 8-bit version stays and the two runtimes differ on a few low-confidence answers. Averaging the last three checkpoints was also tested and made no difference on the tuning data, so the final weights are used.

When the neural answer is used (rule v3)

Chosen on tuning data (hand-written tuning labels, held-out titles, held-out place names): Fast keeps the label when it is a place, an address, or already English, or when Fast knew every word. Otherwise the neural answer is used if its confidence is at least 0.1. The English check on the neural answer was dropped: it rejected good answers full of brand names. A label longer than 8 words is treated as an address only if Fast knew most of its words; long product names with a number and a place word were being mistaken for addresses. Tuning score: labels 80.4, titles 65.0 chrF. These settings ship inside the model file, so Python and JavaScript apply the same rule.

3. What we did, in order

  • v1–v2 (Nov 4–5). Fast: place-name gazetteer (GeoNames), transliteration for 9 scripts, a product word list, an English check. Runs in ~2 ms per label, in Python and in the browser with identical output.
  • v3 (Nov 5–6). First neural model (7M parameters, NLLB teacher, 100 min). Weight study: removing one decoder attention head helped, so it was kept.
  • v4 (Nov 6–8). Three models: A (NLLB), B (OPUS-MT + M2M100, commercial use OK), C (both). 81k product titles, back-translation into 16 languages, restart-safe training, checkpoint averaging, weight edits per model.
  • v5 (Nov 8–10). Teachers' own English answers added as training targets (knowledge distillation, filtered), Tencent Hy-MT2 added as a third teacher, models B2, C2, H, ALL3, HY. Then MAX: no size limit on data, 35k real multilingual product names (ABO), 60k more titles, 10 h training.
  • Products and word combinations (Nov 10). 952 new product words and 2–3 word phrases mined from the Amazon ESCI and ABO catalogues, translated and round-trip checked, added to every model's word list (1,841 automatic terms in total).
  • New decision rule (Nov 10). When to trust the neural model instead of Fast, tuned on held-out training data. Biggest single gain of v5.
  • v6 (Nov 11–12). Review of the whole project, then the final model: a pretrained compact translator fine-tuned on all our data, new short-label data, a SentencePiece tokenizer written for the phone runtime, better 8-bit conversion, a new decision rule.
  • JEPA (Nov 10–11). A self-supervised encoder pretrained to predict the meaning of a label from another language, used two ways, compared against a baseline trained the same total time.

4. Changing the weights after training

After each model finished, I tested switching off each attention head and each feed-forward block one at a time on one held-out slice, kept a change only if it also helped on a second, separate slice, then tried a 15-minute retraining with the change in place. The final call needs the held-out score up and the hand-written labels not down. Checkpoint averaging (mean of the last 3 saved weights) was tested on every model too.

5. Deciding when to use the neural model

Old rule: use the neural model only for the words Fast could not translate. New rule: if Fast understood the label (at least one known word) or it looks like an address, keep Fast; otherwise let the neural model translate the whole label, and keep its answer if it is English and keeps the words Fast was sure of. 6. JEPA

What it is. A Joint-Embedding Predictive Architecture learns by predicting the meaning vector of hidden or translated text instead of the text itself. Here: an encoder reads a label in one language; a predictor must output the vector that a slowly-updated copy of the encoder (EMA target) gives for the English name, and for masked-out spans of the label. No characters are generated, so it learns meaning, not spelling.

Making it work. The first run collapsed: every label got the same vector. Fixed with centering of the target vectors and a variance/covariance penalty (VICReg). Measured by retrieval: among 1,000 held-out pairs, how often the English name nearest to a foreign label's vector is the right one (chance = 0.1%).

Verdict on JEPA. With the same model size, data and total time, JEPA-Gen vs the baseline: -5.4 chrF on labels (model alone), -2.4 on labels (Accurate), -1.3 on real names (Accurate). JEPA pretraining did not pay for its 3 hours; spending them on ordinary translation training was better. JEPA-Gen did start faster (higher held-out scores at the same step, see the chart), so the encoder did learn something useful, but the baseline overtook it once it had the extra time. JEPA tends to help when there is far more unlabeled text than translated pairs; here we have about 400k translated pairs, so plain training learns the same things directly. Decision: JEPA-Gen is not shipped. Lookup: on its own it reaches 10.5 chrF on labels and 30.1 on real names, well below Fast. Tuned on held-out data, the best threshold was to never use it: every setting that let it override Fast lowered the score. The nearest known name is usually a related product, not the same one; label wording varies too much for whole-name lookup.

7. What didn't work

  • Word pieces (BPE) instead of characters. Shorter sequences, but on 4 CPU cores the models stayed stuck repeating common words after hours. Characters learn much faster at this size.
  • A 52M-parameter MAX. About 3× slower per step; in the time available it would have seen too little data. The 22M design wins on CPU.
  • Picking one teacher per language. The held-out data was written by OPUS-MT and NLLB, which biases the choice toward them. Using every teacher's filtered answers works better.
  • Hy-MT2 as main data source (HY). Best teacher, but at ~2.5 s per title only 8k pairs were affordable, and its answers in the mixed models (H, ALL3) did not beat OPUS-MT alone.
  • Large weight cuts and long post-edit retraining. See section 4.
  • Training small models from nothing. The biggest lesson of the review: ten hours of from-scratch CPU training reached 38 on held-out titles; fine-tuning a pretrained model passed that in under 15 minutes and ended at 64.
  • Default 8-bit conversion and 7-bit weights for v6. Both lost too much accuracy; see the v6 section.

9. Recommendation

  • Ship v6 wherever a 106 MB model is acceptable: it more than doubles the exact-match rate on labels and adds over 20 chrF on real names, and its teachers and data allow commercial use (with attribution).
  • Ship v5 MAX (22 MB) when download size or speed matters more: about 10 ms per short label.
  • Fast alone stays the right choice for addresses and place names (~2 ms); every Accurate model keeps using it for those.
  • Next gains: (1) Hy-MT2-7B scores 95 on the labels, so distilling its answers into v6 on a GPU should close much of the remaining gap; (2) Korean is still the weakest language (its word pieces were new to the pretrained model); (3) a smaller v6 by sharing the output layer with the embeddings (about 20 MB less).

10. Conclusions

  1. The goal was reached with v6. The full system goes from 20.0% exact / 42.6 chrF (rules only) to 65.6% / 79.6 on hand-written labels, and from 39.1 to 66.9 chrF on real marketplace names, fully offline.
  2. Starting from a pretrained model mattered more than everything else combined. Seven days of from-scratch models (v3 to v5, twelve of them) moved label chrF from 43 to 51. One 8.5-hour fine-tune of a pretrained translator moved it to 80.
  3. Data that looks like the task beats more data. 35k real product-name pairs lifted real-name scores by 7 points in v5; 58k short labels were a large part of v6's jump on short labels.
  4. The rules (Fast) remain necessary. Place names and addresses are where the neural models are weakest (about 25 chrF on held-out place names) and Fast is near-perfect, so every system keeps Fast for those.
  5. Weight edits help a little, never a lot. Switching off one or two attention heads gained 0.2–1 chrF on about half the small models. For v6 the weight change that mattered was the 8-bit conversion method (+3 chrF over the default).
  6. JEPA worked technically but did not pay off with this much translated data: the same hours spent on ordinary training gave a better model.
  7. Bigger teachers are still far ahead. Hy-MT2-7B scores 95 on the labels. Distilling it into v6 on a GPU is the clearest path to further gains.

12. Important to know

  • Licenses. v6, v5 MAX, B2, H, HY and v4 B were trained only with teachers and data that allow commercial use (OPUS-MT CC BY 4.0, Hy-MT2 Apache-2.0, ABO CC BY 4.0, ESCI Apache-2.0); attribution is required. v3, v4 A, v4 C, C2 and ALL3 used NLLB (CC BY-NC) and are non-commercial. City names need GeoNames attribution. Whether a teacher's license carries over to a model trained on its outputs is not settled law; get legal advice before selling.
  • Speed and size of v6. 106 MB download; 15–75 ms per label on one server core; about 0.1–0.5 s per label in a single-thread browser (measured in Node, not on a real phone). The small models take about 10–65 ms.
  • It still makes mistakes. About one label in three is not an exact match, and some are plainly wrong (an Arabic "non-stick frying pan" came out as "unsticked mattress"). Korean is the weakest language. For anything where a wrong name is costly, show the original next to the translation.
  • Test honesty. The test files were never trained on, but 60 of 320 labels and 103 of 993 real names also occur by coincidence in training text. The "unseen" columns in the v6 section exclude them and are the strict numbers. The 48 unseen address cases were looked at once while choosing a cautious setting for place names; the score did not change.
  • Python and JavaScript. Identical for Fast, the English check and the tokenizer. For v6 they differ on about 1–3% of labels because 8-bit arithmetic rounds differently; measured quality is the same (79.5 vs 79.6 on labels).
  • GitHub. The pull request is a draft and nothing is merged. GitHub's automatic tests have never run because no runner gets assigned (an Actions setting or billing limit on the account); all tests pass when run here.
  • What is not in the repository. The raw training data (several GB, regenerable with the build scripts), full-precision weights and training checkpoints. They exist only in this session's container, which is temporary. Say so if you want them kept.
  • Privacy. All models run on the device; no label text is sent anywhere.
